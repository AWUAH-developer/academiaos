==================================================
1. UPGRADE ELECTRON BEFORE RELEASE
==================================================

The desktop project currently uses Electron 31.

Electron 31 is end-of-support and must NOT be used for the production
AcademiaOS release.

Upgrade the desktop project to the current supported Electron 43 stable
release line.

At the time of this instruction, target Electron 43.2.0 unless compatibility
testing identifies a documented blocking issue.

After upgrading:

- update Electron-related dependencies as required
- rebuild native modules against the Electron version actually shipped
- fix any breaking API changes properly
- run TypeScript checks
- run Electron startup tests
- verify contextIsolation remains true
- verify nodeIntegration remains false
- verify renderer sandboxing remains enabled
- verify navigation/window restrictions remain enabled

Do not downgrade security settings simply to make a dependency work.

==================================================
2. REMOVE KEYTAR DEPENDENCY
==================================================

Do not ship new AcademiaOS production releases depending on the archived
keytar package.

Replace keytar with Electron's built-in safeStorage API for protection of:

- refresh/session secrets where local persistence is required
- the random local SQLite encryption key
- other small machine-local confidential values

Use the asynchronous safeStorage APIs where supported by the Electron
version being shipped.

Windows must use the OS-protected DPAPI-backed storage provided by Electron.

Never hardcode the SQLite encryption key.

Never derive the database encryption key directly from username, school ID,
device ID or password.

Generate a cryptographically random key on first secure setup and protect it
using safeStorage.

==================================================
3. ENCRYPT SQLITE BEFORE ANY WINDOWS RELEASE
==================================================

The current better-sqlite3 implementation is NOT acceptable for production.

Replace it with:

better-sqlite3-multiple-ciphers

Use a current compatible stable release and test it against the chosen
Electron version.

Open the database and apply the encryption key BEFORE any schema read,
migration, query or write that requires access to the encrypted database.

The finished local database must not be readable as ordinary plaintext
SQLite.

Test this explicitly:

1. Sign in.
2. Create cached/offline records.
3. Close AcademiaOS.
4. Attempt to open the local .db file using ordinary unencrypted SQLite.
5. Confirm the protected database contents cannot be read.
6. Reopen AcademiaOS.
7. Confirm safeStorage retrieves the protected key and the app can open the
   database normally.

Also provide a safe migration strategy in case a development plaintext local
database already exists.

Development databases must never silently become a production security
weakness.
